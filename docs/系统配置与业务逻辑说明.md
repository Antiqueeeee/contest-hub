## 一、配置体系总览

系统的可配置项分三层,改动方式、生效时机各不相同:

| 层级 | 在哪配置 | 生效时机 | 举例 |
|---|---|---|---|
| ① 环境变量 | 服务器 `.env`(docker-compose 注入容器) | 重启服务后 | JWT_SECRET、PUBLIC_QUERY_IP_LIMIT |
| ② 系统设置 | 管理后台「系统设置」页 | 立即生效,无需重启 | 数据保留天数、未成年人保护开关 |
| ③ 赛事配置 | 管理后台创建/编辑赛事 | 立即生效,作用于该赛事 | 报名窗口、评分项、名额、未成年人政策 |

## 二、环境变量(部署级,`.env`)

> 完整示例见 `.env.example`。三个必填项不填服务拒绝启动。

### 2.1 必填项

| 变量 | 作用 | 为什么这么设计 |
|---|---|---|
| `DB_PASSWORD` | 数据库密码 | 可含特殊字符,系统自动 URL 编码 |
| `JWT_SECRET` | 登录令牌(JWT)签名密钥,**≥32 字节随机值** | 所有登录态(管理员+选手)都由它签名。弱密钥 = 攻击者可伪造管理员令牌直接控制整个后台(2026-08 安全扫描真实打穿过一次,现已启动时强制校验长度)。生成命令:`python -c "import secrets; print(secrets.token_urlsafe(32))"` |
| `ENCRYPTION_KEY` | 身份证号/手机号/邮箱等敏感字段的加密密钥 | Fernet 对称加密。**一旦启用绝不能换**——换了解不开库里所有已加密数据(选手连登录都登不上,邮箱盲索引也失效)。生成命令:`python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"`。仅发生数据泄露需要应急预案时才轮换(见 `docs/incident-response.md`) |

### 2.2 可选配置

| 变量 | 默认 | 作用 | 为什么这么设计 / 注意事项 |
|---|---|---|---|
| `JWT_EXPIRE_MINUTES` | 120 | 登录令牌有效期(分钟) | 等保 2.0 会话管理要求:过期自动登出。管理员被禁用后 token 也立即失效(每次请求回查数据库),不依赖过期时间 |
| `ALLOWED_ORIGINS` | http://localhost | CORS 允许的前端来源,逗号分隔 | 生产必须改成实际域名,否则浏览器跨域拦截 |
| `FORCE_HTTPS` | false | 开启后敏感接口(登录/注册/导出/选手接口/公开报名)在非 HTTPS 请求下直接拒绝,并返回 HSTS 响应头 | 等保 2.0 通信保密性要求。**前提**:外层代理必须总是覆写 `X-Forwarded-Proto`(不能透传客户端原值,否则攻击者可伪造)、且 `TRUST_PROXY=true`。没配好 HTTPS 前不要开 |
| `TRUST_PROXY` | false | 信任前端 nginx 透传的代理头 | 有外层 HTTPS 网关时必须设 true |
| `PORT` | 80 | 前端对外端口 | 外层网关转发目标 |
| `PUBLIC_QUERY_IP_LIMIT` | 30 | 成绩查询接口的"按 IP 聚合限流"(次/分钟) | 防攻击者轮换报名编号枚举全部选手成绩。**关键**:多层代理(有外层网关)时所有用户共享外层代理 IP,这个桶退化成"全站总限额"——放榜日几百人同时查会大面积 429,所以有外层网关时建议调到 300-600;单层部署(docker-compose 直连)按真实客户端 IP 计,保持默认即可 |
| `UPLOAD_MAX_SIZE_MB` | 10 | 图片上传大小上限 | 轮播图等图片防滥用 |
| `EXPORT_MAX_ROWS` | 50000 | 单次导出最大行数 | 防超大导出拖垮服务器 |
| `RATE_LIMIT_MULTIPLIER` | 1 | 限流阈值放大倍数 | **仅 e2e 自动化测试用,生产不要设置**(设了等于放宽全部限流) |
| `DEBUG` | true | 开发调试标志 | 生产应关闭 |

> `EXPORT_DIR`/`UPLOAD_DIR` 在 docker-compose 中固定为容器内目录并挂载为卷,一般不需要改。

## 三、系统设置(管理后台「系统设置」页,立即生效)

| 设置项 | 默认 | 作用 | 为什么这么设计 |
|---|---|---|---|
| 报名数据保留天数 | 180 天 | 赛事结束后,匿名报名的身份证号(及未成年人字段)保留这么久后自动清除 | 个保法最小必要原则:留到申诉/复核期结束即可删,不必永久留存。**账号报名的不受此影响**——数据在选手自己账号里,选手可随时注销清除 |
| 已删除报名清除天数 | 30 天 | 管理员软删除的报名记录,30 天后物理清除 | 给误删留反悔窗口;有成绩的报名不会被物理删除(成绩链优先) |
| 导出文件保留天数 | 1 天 | 导出的 Excel 在服务器上保留多久自动删除 | 导出文件含明文身份证号,属机密文件,越短越安全;客户端手册要求下载后当机密对待 |
| 审计日志 IP 匿名化天数 | 183 天 | 审计日志满 183 天后,IP 地址匿名化处理 | 网络安全法要求日志留存 ≥6 个月;满期后匿名化是"留存义务"与"个人信息最小化"的折中 |
| 未成年人保护模块 | 关 | 系统级总开关 | 见第四节,三级开关第一级 |
| 选手注册开关 | 开 | 关闭后前台停止新选手注册(已注册选手不受影响) | 报名截止/应急时一键关闭 |

## 四、赛事配置(管理后台创建/编辑赛事)

### 4.1 赛事状态机

`草稿 draft → 开放报名 open → 进行中 ongoing → 已结束 finished`,另有 `已取消 cancelled`。
只有 `open` 状态接受报名;状态流转在后台操作。**为什么报名检查在服务端而非只靠前端**:状态、报名窗口、名额、去重全部服务端校验,绕过页面直接调接口也会被拦。

### 4.2 报名窗口与比赛时间

- `报名开始/截止`(精确到秒):在此之外提交一律 400"报名尚未开始/已截止"
- `比赛开始/结束`(按日期):用于**年龄判定**(未成年人模块按"赛事开始日"算年龄,不是报名日——见 4.5)和成绩发布周期

### 4.3 时区

赛事有自己的时区(如 Asia/Shanghai),报名窗口按赛事时区解析。**为什么**:避免服务器 UTC 时间与本地赛事时间混淆(历史上真实踩过坑)。

### 4.4 评分项与组别

- `评分项`(如"客观题得分/主观题得分"):决定成绩录入、模板、导出的列
- `组别` + `每组名额上限`:报满即拒("该组别名额已满")

### 4.5 未成年人政策(赛事级开关)

`normal`(普通赛事)/ `minors_welcome`(面向未成年人)——未成年人保护模块的第二级开关。

## 五、报名业务逻辑

### 5.1 两种报名方式

| | 匿名报名 | 账号报名 |
|---|---|---|
| 流程 | 前台直接填表(姓名/邮箱/身份证号) | 选手注册登录后报名 |
| 身份证号存储 | 加密存进报名记录,保留期满自动清除 | 首次提交时**绑定到账号**(懒收集),报名记录不冗余存储 |
| 好处 | 降低参与门槛 | 一次绑定、后续赛事免填;注销账号即彻底清除 |

### 5.2 敏感信息单独同意

提交身份证号必须单独勾选"身份证号同意"(与隐私政策同意分开)。**为什么**:个保法要求敏感个人信息(身份证号属于)取得单独同意,且同意记录落库,作为将来举证凭证。

### 5.3 去重与名额(服务端强制)

- 同一账号在同一赛事同一组别只能报一次(含双击/并发重复提交,唯一索引兜底)
- 同一身份证号跨账号重复报名会被拦(匿名报名比对密文、账号报名比对账号证号)
- 名额满后拒绝

### 5.4 报名编号

格式 `C001-20260816-0001`(赛事 ID-日期-当日序号)。**为什么用顺序号而不是随机号**:要印在参赛证/成绩单上,人可读、可对号;防枚举由成绩查询接口的限流承担(见第七节)。

### 5.5 自定义报名字段

报名表单可携带自由扩展字段(custom_fields),原样存储、可导出。**系统会强制剥离与内置字段同名的键**(name/email/身份证号/出生日期/监护人等,防止攻击者用它覆写加密数据或绕过去重)。客户手册明确提醒:**不要用自定义字段收集敏感信息**(它不加密)。

## 六、未成年人保护模块(三级开关)

> 完整设计见 `docs/未成年人保护模块设计.md`,此处是业务视角摘要。

### 6.1 三级开关,缺一不可

1. **系统级**:后台「系统设置」里打开模块总开关(默认关——不启用时一切流程与普通赛事完全一致)
2. **赛事级**:赛事编辑时设 `minors_welcome`
3. **年龄分支**:两个开关都开时,报名流程按年龄走不同分支

### 6.2 年龄分支

| 年龄(按赛事开始日) | 要求 | 效果 |
|---|---|---|
| < 14 周岁 | 监护人姓名 + 联系方式 + 监护人单独同意 | 落实《儿童个人信息网络保护规定》的监护人同意 |
| 14-17 周岁 | 本人勾选"已满 14 周岁"声明 | 落实 14 岁以上未成年人本人同意规则 |
| ≥ 18 周岁 | 无额外要求 | — |

### 6.3 关键设计点(为什么)

- **年龄按赛事开始日计算**,不是报名日——报名时 13 岁、开赛时 14 岁,按 14 岁规则走,避免资格误判
- **出生日期必须与身份证号内嵌日期一致**(18 位身份证第 7-14 位就是生日)。**为什么**:防止未成年人把生日虚报成 1980 年跳过监护人同意(2026-08 安全扫描发现的绕过)。匿名报名不一致直接拒绝;账号报名不一致时**以校验位合法的身份证号为准自动更正**(避免个人中心改证号后被永久卡死)
- **出生日期/监护人信息只在必要时收集**(懒收集),加密存储、接口一律脱敏展示(如 `2012-**-**`、`张**`)
- **监护人同意可撤回**:撤回即清除账号上的出生日期与监护人信息,再次报名需重新收集
- 同意记录(隐私政策/身份证/监护人/14 周岁声明)全部落库留痕

## 七、成绩管理

### 7.1 录入 → 发布 → 查询

1. 管理员下载**成绩导入模板**(预填报名编号与姓名,可直接填分)
2. 导入/手工录入成绩 → 保存为草稿
3. **发布**:发布后选手才能查到;可**撤回**(撤回后前台查不到)

### 7.2 公开查询(无需登录)

前台用「报名编号 + 邮箱」查询成绩。**为什么不需要登录**:选手可能没注册账号(匿名报名)。**为什么还要邮箱**:防止仅凭报名编号(顺序号可枚举)就能翻出别人成绩。**为什么有限流**:两层——每个报名编号 10 次/分钟(防单点爆破)+ 每个 IP 30 次/分钟(防轮换编号枚举,即 `PUBLIC_QUERY_IP_LIMIT`,见第二节)。

## 八、数据导出与脱敏规则

### 8.1 三种导出

| 导出 | 内容 | 保留期 |
|---|---|---|
| 报名数据 | 报名编号/姓名/邮箱/身份证号/学校/组别/报名时间 + 自定义字段 | 服务器 1 天(可配) |
| 成绩数据 | 报名编号/姓名/各评分项/总分/排名/奖项 | 同上 |
| 成绩导入模板 | 预填报名编号与姓名,供填分导入 | 同上 |

### 8.2 脱敏规则(什么脱敏、什么不脱敏,为什么)

| 数据 | 导出时 | 为什么 |
|---|---|---|
| 身份证号 | **明文**(可配字段) | 报名去重、现场核验需要完整号码,是已接受的业务需求 |
| 出生日期/监护人姓名/联系方式(未成年人) | **一律脱敏**(`2012-**-**`、`张**`) | 比身份证更敏感的儿童信息,只允许以脱敏形式离开平台 |
| 接口返回 | 身份证一律 `320102****1234` 形式 | 展示层最小化 |

### 8.3 公式注入防护

姓名/邮箱等用户提交的值若以 `= + - @` 等字符开头,导出时统一加单引号前缀转义。**为什么**:否则选手报名时把姓名填成 `=HYPERLINK(...)` 或 DDE 命令,管理员打开 Excel 就会执行攻击者的公式(2026-08 安全扫描发现的存储型漏洞)。

## 十、安全与合规机制清单(系统自动做的,不用手动配置)

| 机制 | 说明 |
|---|---|
| 传输加密 | 外层 HTTPS + 可选 HSTS(FORCE_HTTPS) |
| 存储加密 | 身份证/手机号/邮箱 Fernet 加密;邮箱另有盲索引支持等值查询(加密但不牺牲功能) |
| 认证 | 管理员与选手双命名空间 token(type claim 严格区分,防止选手 token 冒充管理员);管理员密码复杂度 8-64 位至少两类字符;登录失败限流 |
| 会话 | 120 分钟过期;管理员禁用/选手注销后 token **立即失效**(每次请求回查数据库) |
| 限流 | 登录 10 次/分钟、密码修改 5 次/分钟、公开报名 20 次/分钟、导出 10 次/分钟、成绩查询 10+30 次/分钟等,全接口覆盖 |
| 审计日志 | 登录成败、增删改(赛事/新闻/用户/成绩/导出/报名)全记录;IP 满 183 天匿名化 |
| 数据生命周期 | 软删除 → 保留期 → 物理清除;匿名报名 PII 赛事结束 180 天后清除 |
| 备份 | 每天自动 pg_dump(按上线指南配置) |

## 十一、关键"为什么"速查(FAQ)

**Q:JWT_SECRET 和 ENCRYPTION_KEY 都是密钥,区别是什么?**
JWT_SECRET 是"门禁卡"——轮换只是所有人重新登录一次,数据无损;ENCRYPTION_KEY 是"保险箱钥匙"——轮换等于换锁,已加密的数据全部读不出来,永远别动它。

**Q:为什么导出文件服务器只留 1 天?**
因为导出内容含明文身份证号。留得越短,泄露面越小;需要存档请客户自行安全保存。

**Q:为什么成绩查询既有 10 次/分钟又有 30 次/分钟两层限制?**
攻击手法:用不同报名编号轮换查询,把每个编号的 10 次限额逐个耗尽,从而枚举全部选手成绩。第一层防单点爆破,第二层(按 IP)防轮换枚举。有外层网关时第二层按全站计,所以要调大 `PUBLIC_QUERY_IP_LIMIT`,防枚举仍由第一层兜底。

**Q:为什么出生日期必须和身份证一致,不一致还会"自动更正"?**
身份证第 7-14 位编码出生日期,自报生日必须与之吻合,否则未成年人可虚报成人年龄绕过监护人同意。账号场景下以证号为准自动更正,是防止"个人中心改证号 → 生日对不上 → 永久无法报名"的死锁(证号是校验位合法的更强凭据,更正只会让年龄判定更准确)。

**Q:为什么管理员禁用后立即失去权限,而不是等 token 过期?**
被辞退/换岗的管理员在 120 分钟内仍可操作是不可接受的。每请求回查数据库的代价(一次主键查询)对管理后台可忽略。

**Q:报名编号为什么是顺序的,不会被人猜吗?**
顺序号是为了参赛证上人可读、可对号。猜编号不等于能看成绩——还需要匹配的邮箱,并且有限流封顶。若未来要更强的匿名性,可加随机查询码(当前版本未做,见合规缺口文档)。

# 数据安全事件应急预案

> 版本：v1.0（2026-07-26）
> 法律依据：《数据安全法》第 29 条、《个人信息保护法》第 57 条、GB/T 22239-2019（等保 2.0）
> 适用范围：竞赛信息发布平台（FastAPI + PostgreSQL，Docker Compose 部署）

---

## 一、事件分级

按影响范围和涉及数据的敏感程度，将数据安全事件分为三级：

| 级别 | 判定标准（满足任一即构成） | 示例 |
|------|---------------------------|------|
| **重大** | 泄露身份证号（敏感个人信息）≥ 1000 条；或数据库整体被拖库、被勒索加密；或平台被入侵且攻击者获得管理员权限 | 服务器被入侵，`contest_hub` 库被整库导出 |
| **较大** | 泄露身份证号 100–999 条；或泄露姓名/邮箱/单位等一般个人信息 ≥ 1000 条；或导出文件（含明文身份证号的 Excel）外泄 | 管理员电脑丢失，内有未删除的导出 Excel |
| **一般** | 泄露身份证号 < 100 条；或一般个人信息 < 1000 条；或发现入侵尝试但未造成数据泄露 | 审计日志发现异常批量查询，经核实未导出数据 |

级别判定时以「实际或可能泄露的数据条数 × 敏感程度」为准；无法确定条数时，按就高原则先升一级处置。

## 二、组织与职责

| 角色 | 人员 | 职责 |
|------|------|------|
| 应急负责人 | 【待填写：姓名 + 手机 + 邮箱】 | 事件定级、启动预案、对外报告（主管部门）、决策停机/恢复 |
| 技术联系人 | 【待填写：姓名 + 手机 + 邮箱】 | 封堵、取证、日志分析、系统恢复 |
| 个人信息保护负责人 | 【待填写：姓名 + 邮箱】 | 评估个人信息影响、起草并发出用户通知 |

任何人员发现疑似事件，应**立即**电话通知应急负责人和技术联系人，不得自行处理后再上报。

## 三、响应流程

### 1. 发现与初判（0–1 小时）

可能的发现渠道：

- 审计日志告警：`audit_logs` 表中的异常事件（登录暴破、异常导出、批量查询）
- 用户举报、第三方通报、媒体曝光
- 运维发现服务异常（CPU/流量突增、异常进程）

初判要点：确认事件类型（泄露 / 篡改 / 丢失 / 不可用）、涉及的数据表和时间范围，初步定级并启动本预案。

### 2. 封堵与止损（立即执行）

按事件类型选择以下操作（在项目根目录 `/opt/contest-hub` 下执行）：

```bash
# 情况 A：确认外部入侵或泄露正在进行 —— 直接停掉对外服务
docker compose stop backend frontend

# 情况 B：怀疑登录令牌（JWT）已泄露 —— 更换签名密钥使所有旧 token 失效
# 1. 生成新密钥
python -c "import secrets; print(secrets.token_urlsafe(32))"
# 2. 修改 .env 中的 JWT_SECRET 为新值
# 3. 重启后端使新密钥生效（所有用户需重新登录）
docker compose restart backend

# 情况 C：怀疑加密密钥（ENCRYPTION_KEY）或数据库口令泄露
# 修改 .env 中的 DB_PASSWORD，并同步修改 db 服务的环境变量后重建：
docker compose up -d --force-recreate db backend
# 注意：更换 ENCRYPTION_KEY 会导致已加密的身份证号无法解密，
# 需先用旧密钥解密再用新密钥重新加密，操作前务必先备份（见下）。

# 情况 D：某一管理员账号被盗用
# 在管理后台禁用该账号并修改密码；同时按情况 B 吊销其 token
```

### 3. 取证（封堵后、清理前）

**先取证，后清理**。保留现场证据：

```bash
# 导出数据库全量快照（取证用，注意该文件含明文敏感数据，须加密保管）
docker compose exec -T db pg_dump -U contest contest_hub | gzip > evidence_$(date +%Y%m%d_%H%M%S).sql.gz

# 导出相关时间段的审计日志
docker compose exec -T db psql -U contest -d contest_hub -c \
  "COPY (SELECT * FROM audit_logs WHERE created_at >= '事件开始时间' ORDER BY created_at) TO STDOUT WITH CSV HEADER" \
  > evidence_audit_logs.csv

# 保存容器日志
docker compose logs --since 24h backend  > evidence_backend.log 2>&1
docker compose logs --since 24h frontend > evidence_frontend.log 2>&1
docker compose logs --since 24h db       > evidence_db.log 2>&1
```

取证文件统一保存到独立目录，记录文件哈希（`sha256sum`），限制访问权限（`chmod 600`），不得随意修改或删除。

### 4. 评估（24 小时内完成）

技术联系人与应急负责人共同确认：

- 涉及的数据种类与数量：身份证号 ___ 条、姓名/邮箱/单位 ___ 条、其他 ___
- 数据是否已实际外泄（对比服务器外发流量、审计日志中的导出/查询记录）
- 影响的用户范围（从 `contestants`、`registrations` 表按赛事/时间段圈定）
- 事件根因（漏洞、弱口令、内部人员、运维失误）
- 最终定级

### 5. 通知（见第四节）

### 6. 恢复与复盘

- 修复根因（打补丁、改口令、加配置）后逐步恢复服务：`docker compose up -d`
- 恢复后持续观察审计日志 ≥ 7 天，确认无复发
- 事件结束后 5 个工作日内完成复盘报告（见第六节）

## 四、通知要求与时限

| 通知对象 | 触发条件 | 时限 | 依据 |
|----------|----------|------|------|
| 主管部门（网信部门/行业主管部门） | 较大及以上事件；一般事件涉及个人信息泄露的也需报告 | **24 小时内** | 数据安全法第 29 条 |
| 受影响的个人 | 泄露涉及其个人信息（姓名、身份证号、邮箱、单位等） | 评估确认后尽快，不晚于报告主管部门后 72 小时 | 个保法第 57 条 |

**例外**：采取措施能够有效避免信息泄露造成危害的，可以不通知个人；但主管部门认为可能造成危害并要求通知的，仍应通知（个保法第 57 条）。

通知渠道：

- 个人：注册邮箱逐一发送（数据源：`contestants.email`）；同时在平台首页发布事件公告
- 主管部门：按属地网信部门要求的渠道（书面/电话/指定平台）报告

## 五、事后复盘与记录留存

事件结束后 5 个工作日内，应急负责人组织复盘，输出复盘报告，内容包括：

- 事件时间线（发现→封堵→取证→恢复各节点时间）
- 根因分析与定级结论
- 处置过程中的问题与不足
- 整改措施清单（责任人、完成时限）

**记录留存要求**：

- 复盘报告、通知记录（发送清单、主管部门回执）、取证文件清单一并归档，**至少保存三年**
- 事件本身及处置动作应补记到 `audit_logs`（event_type 使用安全事件类），保证日志链完整

## 六、日常预防（与现有机制衔接）

本预案依赖平台已有的以下机制，日常应保证其有效运行：

- **审计日志**：`audit_logs` 表记录认证行为、敏感操作、数据变更、安全事件（含 IP、UA），保留 ≥6 个月，是事件发现和取证的主要数据源。运维应定期抽查异常事件（如高频登录失败、非工作时间导出）
- **数据库备份**：`scripts/backup.sh` 每日定时备份（保留 30 天），发生数据篡改/丢失/勒索事件时用于恢复；恢复命令见 README「数据备份」一节
- **登录防护**：登录失败锁定（同账号 5 次失败锁 15 分钟、同 IP 10 次失败拒 15 分钟）与接口限流已启用，相关事件计入审计日志
- **数据加密**：身份证号以 Fernet 加密存储、接口脱敏返回，可降低泄露后的实际危害
- **导出文件清理**：含明文身份证号的导出 Excel 由后台任务按 `export_retention_days`（默认 1 天）自动删除，减少外泄面

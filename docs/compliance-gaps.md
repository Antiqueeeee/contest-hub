## 二、个人信息保护法（PIPL）差距

本平台收集的个人信息包括：姓名、身份证号（属敏感个人信息）、手机号、邮箱、组织单位。

### 2.1 隐私政策缺失 — 第 17 条（🔴 P0）— 2026-07-26 已修复

> 个人信息处理者在处理个人信息前，应当以显著方式、清晰易懂的语言真实、准确、完整地向个人告知：处理目的、处理方式、种类、保存期限、个人行使权利的方式和程序……

**现状：** 平台没有任何页面展示隐私政策，首页没有入口，用户注册和报名时也无从查看平台将如何处理其个人信息。

**需修复：**（2026-07-26 已全部完成）
- [x] 新建隐私政策内容页（内容包括：收集哪些信息、用于什么目的、保存多久、用户有哪些权利、如何联系平台）
- [x] 首页底部添加「隐私政策」链接
- [x] 注册页面添加隐私政策链接和勾选确认（详见 2.2）
- [x] 报名页面添加隐私政策链接（如已存在则需确保链接可点击跳转至政策全文）

---

### 2.2 明示同意 — 第 14 条（🔴 P0）— 2026-07-26 已修复

> 基于个人同意处理个人信息的，该同意应当由个人在充分知情的前提下自愿、明确作出。

**现状共两个场景均有问题：**

**场景一：选手报名表单。** 系统虽然展示了一个「我已阅读并同意《隐私政策》」勾选框，但用户即使不勾选，系统后端也会默认当作"已同意"来处理。这意味着用户在不知情的情况下就被视为同意，无法体现"自愿、明确"的同意。

**场景二：选手注册账号页面。** 注册时需要填写姓名、身份证号、邮箱等个人信息，但页面上完全没有隐私政策相关的告知或同意勾选框，用户无从知晓平台将如何处理这些信息。

**需修复：**（2026-07-26 已全部完成）
- [x] 报名接口中"是否同意隐私政策"字段的默认值从「同意」改为「不同意」（后端）— 已改为必填且必须为 true，无默认值
- [x] 报名表单上的隐私政策勾选框默认不勾选，用户不勾选时明确提示并禁止提交
- [x] 选手注册账号页面新增隐私政策告知和独立勾选框（「我已阅读并同意《隐私政策》」），默认不勾选
- [x] 《隐私政策》文字应为可点击链接，点击后能查看政策全文
- [x] 将同意记录持久化（注册/报名时记录 privacy_agreed、id_number_agreed 及时间戳、政策版本），以满足个保法下平台"能够证明已取得同意"的举证责任 — 2026-07-26 第三轮完成：consent_logs 流水表（含政策版本与 IP）

---

### 2.3 敏感个人信息单独同意 — 第 30 条（🔴 P0）— 2026-07-26 已修复

> 个人信息处理者处理敏感个人信息的……应当取得个人的单独同意。

**现状：** 身份证号属于法律明确定义的"敏感个人信息"，但目前在报名页面和注册页面中，身份证号的收集被混在一般信息中一并勾选同意，没有单独的提示和单独的同意。

**需修复：**（2026-07-26 已全部完成）
- [x] 在注册和报名页面中，身份证号字段旁增加醒目提示语：「您的身份证号属于敏感个人信息，仅用于赛事报名核验，不会公开」— 注册已不再收集身份证号，提示语加在报名页和个人中心绑定处
- [x] 在隐私政策同意之外，增加一个独立的「同意收集身份证号」勾选框（仅在用户实际填写了身份证号时需要勾选）
- [x] 两个同意不可捆绑——用户同意隐私政策不代表同意收集身份证号

---

### 2.4 删除权 / 注销账号 — 第 47 条（🟡 P1）— 2026-07-26 已修复

> 个人有权请求删除其个人信息……个人信息处理者应当提供便捷的撤回同意和删除方式。

**现状：** 选手用户没有自助注销账号的途径。如果要删除账号，必须联系管理员人工处理。

**需修复：**（2026-07-26 第三轮已全部完成）
- [x] 选手个人中心增加「注销账号」入口（「隐私与安全」区域，需密码确认）
- [x] 注销时明确告知用户注销后果（报名记录去标识化保留、成绩记录保留等）
- [x] 注销逻辑：标记账号为已注销（deleted_at）+ 脱敏保留报名记录关联（不可物理删除报名记录，否则赛事成绩记录会断裂）
- [x] 注销后该选手的身份证号、手机号、邮箱在数据库中脱敏处理（不可恢复为明文）— 姓名匿名化为「已注销用户」、身份证号/单位置空、邮箱改写为 `deleted_{id}@deleted.invalid`（释放原邮箱）、密码哈希随机化、token 立即失效

---

### 2.5 查阅与复制权 — 第 45 条（🟡 P1）— 2026-07-26 已修复

> 个人有权向个人信息处理者查阅、复制其个人信息。

**现状：** 选手个人中心只能编辑姓名、邮箱、单位，没有「查看我的完整个人信息」或「下载我的个人数据」功能。用户无法确认平台到底存了哪些关于自己的数据，也无法获取一份副本。

**需修复：**（2026-07-26 第三轮已全部完成）
- [x] 选手个人中心增加「查看我的个人信息」页面，展示平台存储的所有用户数据（含脱敏后的身份证号）— `GET /api/contestant/my-data` 返回账号信息+报名+成绩+同意记录
- [x] 提供「导出个人数据」功能，将用户信息（含报名记录）打包为可下载文件 — 个人中心一键下载 JSON

---

### 2.6 撤回同意权 — 第 15 条（🟡 P1）— 2026-07-26 已修复

> 基于个人同意处理个人信息的，个人有权撤回其同意。个人信息处理者应当提供便捷的撤回同意方式。

**现状：** 平台没有提供任何撤回同意的入口。撤回同意权是独立于注销账号的权利——用户可能希望保留账号继续参赛，但撤回对某些非必要处理活动的同意（例如不再接收通知、不参与数据分析）。

**需修复：**（2026-07-26 第三轮已全部完成）
- [x] 个人中心增加「隐私设置」或「授权管理」页面
- [x] 列出用户已同意的各项处理活动，让用户可以逐项撤回 — 身份证号同意可单独撤回；隐私政策同意为基础服务所必需，撤回路径为注销账号（页面有明确说明）
- [x] 撤回同意后，相应的处理活动应立即停止 — 撤回身份证号同意即删除账号上绑定的证号（不可恢复），后续报名需重新收集并单独同意

---

### 2.7 最小保存期限与自动清理 — 第 19 条（🟡 P1）— 2026-07-26 已修复（一项除外）

> 个人信息的保存期限应当为实现处理目的所必要的最短时间。

**现状：** 报名数据（含姓名、身份证号、邮箱等）在赛事结束后永久保留，没有自动清理机制。虽然删除报名时提示"数据将在 30 天后自动清除"，但实际上没有对应的自动清理逻辑。

**需修复：**
- [x] 赛事结束后 N 天（建议 180 天），自动清理报名数据中的身份证号字段（置空或脱敏）— 每日清理任务，默认 180 天，匿名报名的 form_data 证号清除（账号报名本就不存证号）
- [x] 已完成赛事的报名表单数据中涉及的身份证号，在导出后/赛事结束后自动清除 — 同上机制覆盖
- [x] 系统增加可配置的数据保留天数设置项 — `system_settings` 表 + 后台「系统设置」页（报名保留 180 天、软删清除 30 天、导出文件 1 天）
- [x] 导出文件（含解密的身份证号）在服务器上的保留时间应尽可能短，建议不超过 24 小时 — 默认保留 1 天，每日自动删除
- [ ] 导出文件应加密存储 — 未做：文件在服务器文件系统内明文存放（保留 1 天），依赖主机访问控制；如需更高保障可后续加密

### 2.8 邮箱明文存储 — 第 51 条（🟡 P1）

> 个人信息处理者应当采取加密、去标识化等安全技术措施。

**现状：** 选手的邮箱地址在数据库中明文存储，而同一系统中管理员的手机号已做了加密存储。邮箱属于个人信息，在发生数据库泄露时，明文邮箱将直接暴露用户隐私。

**需修复：**
- [ ] 选手邮箱字段改为加密存储（与管理员的手机号采用相同加密方案）
- [ ] 评估选手姓名是否也需要加密存储

**现状：** 未做。

**需修复：**
- [x] 编写 PIA 报告文档（`docs/pia-report.md`），内容包括：处理目的、种类、必要性分析、风险识别、保护措施、评估结论 — 2026-07-26 已完成草稿，评估人/结论需运营方确认签署

### 2.10 向第三方提供个人信息的告知同意 — 第 23 条（🟢 P2）

> 个人信息处理者向其他个人信息处理者提供其处理的个人信息的，应当向个人告知接收方的名称或者姓名、联系方式、处理目的、处理方式和个人信息的种类，并取得个人的单独同意。

**现状：** 如果赛事报名数据需要提供给赛事主办方、承办方或其他合作方，平台目前没有相关的告知和同意机制。对于竞赛平台而言，数据的流转几乎是必然会发生的。

**需修复：**
- [ ] 梳理数据流转关系：明确哪些数据会提供给哪些接收方
- [ ] 在报名环节增加告知（接收方是谁、用途是什么）
- [ ] 如需共享身份证号等敏感信息，需取得用户的单独同意
- [ ] 与数据接收方签署数据处理协议

### 2.11 个人信息保护负责人 — 第 52 条（🟢 P2）

> 处理个人信息达到国家网信部门规定数量的个人信息处理者，应当指定个人信息保护负责人，负责对个人信息处理活动以及采取的保护措施等进行监督。

**现状：** 平台未指定个人信息保护负责人，隐私政策或网站上也未公开负责人的联系方式。

**需修复：**
- [ ] 指定一名个人信息保护负责人
- [ ] 在隐私政策页面中公开其联系方式（至少包括邮箱）
- [ ] 将该负责人信息报送相关部门（如适用）

### 2.12 定期合规审计 — 第 54 条（🟢 P2）

> 个人信息处理者应当定期对其处理个人信息遵守法律、行政法规的情况进行合规审计。

**现状：** 未建立定期审计机制。注意此项与第 55 条的 PIA（个人信息保护影响评估）是两项不同的义务——PIA 是在处理敏感个人信息之前做的评估，合规审计是定期对整体合规情况进行审查。

**需修复：**
- [ ] 建立年度合规审计机制（自行审计或委托外部机构）
- [ ] 留存审计记录

---

### 2.13 个人信息泄露通知义务 — 第 57 条（🟢 P2）— 2026-07-26 已完成

> 发生或者可能发生个人信息泄露、篡改、丢失的，个人信息处理者应当立即采取补救措施，并通知履行个人信息保护职责的部门和个人。

**现状：** 未建立数据泄露通知流程。（数据安全法部分提到了应急预案，但个保法对通知的内容和时限有独立要求。）

**需修复：**（2026-07-26 已完成）
- [x] 在数据泄露应急预案中明确个保法第 57 条要求的通知流程（通知部门 + 通知个人）— `docs/incident-response.md`
- [x] 明确通知内容模板：泄露事件描述、可能影响、已采取措施、用户如何降低风险、联系方式 — 用户通知与监管报告两份模板

---

### 2.14 最小必要原则审查 — 第 6 条（🟢 P3）

> 收集个人信息，应当限于实现处理目的的最小范围，不得过度收集个人信息。

**现状：** 选手注册账号时，身份证号是必填项。但对于仅浏览赛事信息的用户，身份证号并非必需——只有报名时才真正需要身份证号。

**需修复：**
- [x] 评估是否可以将账号注册与身份证号收集解耦（注册只需邮箱+密码+姓名，报名时再收集身份证号）— 2026-07-26 已实施：首次报名时绑定账号并复用，报名记录不冗余存储
- [ ] 对每个收集字段进行必要性论证并记录 — PIA 报告（`docs/pia-report.md`）已覆盖主要字段，自定义字段的逐字段论证待补充

---

### 2.15 自动化决策透明度 — 第 24 条（🟢 P3）

> 个人信息处理者利用个人信息进行自动化决策的，应当保证决策的透明度、结果公平公正，不得对个人在交易价格等交易条件上实行不合理的差别待遇。通过自动化决策方式作出对个人权益有重大影响的决定，个人有权要求予以说明，并有权拒绝仅通过自动化决策方式作出决定。

**现状：** 如系统涉及自动评分、自动排名、自动评奖等逻辑，目前没有相关的透明度说明和拒绝权入口。

**需修复：**
- [ ] 如存在自动化决策，在相应页面说明决策逻辑
- [ ] 提供人工复核渠道

---

### 2.16 报名自定义字段缺乏管控（🟢 P2）

**现状：** 管理员可以为报名表单添加任意自定义收集字段（自由文本、下拉选项等），目前没有机制阻止管理员通过这些自定义字段收集敏感个人信息（如健康状况、民族、宗教信仰、生物特征等）。如果管理员添加了此类字段，平台作为数据处理者可能面临合规风险。

**需修复：**
- [ ] 对自定义字段的内容进行审查（禁止收集与赛事无关的敏感信息）
- [ ] 或在添加字段时由系统给出提醒，并要求管理员确认字段不涉及敏感个人信息

## 三、数据安全法（DSL）差距

### 3.1 数据分类分级 — 第 21 条（🟢 P2）

> 国家建立数据分类分级保护制度。

**现状：** 系统中没有对数据字段进行分级标识。

**需修复：**
- [ ] 制定数据分级标准：身份证号=敏感级，姓名/手机/邮箱=一般个人信息，赛事信息=业务数据
- [ ] 在数据库设计文档中标注敏感字段级别

**需修复：**

- [ ] 限制能查看操作日志的人员范围
